# Project Development Plan — Bike Booking SaaS

แผนการพัฒนาโปรเจกต์เชิงลึกสำหรับระบบ **Bike Booking SaaS** เพื่อปิดช่องว่างสถาปัตยกรรม (Implementation Gaps) และผลักดันระบบให้พร้อมรองรับร้านค้าแบบสมบูรณ์

---

## 📌 ขั้นตอนที่ 1: ตรวจสอบและทดสอบระบบเข้าสู่ระบบควบคุม (Control Login Verification)

### สิ่งที่จะทำ:
1. ตรวจสอบการทำงานของ `control.craftbikelab.com/login` ว่าสามารถแยกแยะบทบาทผู้ใช้ระดับผู้ดูแลระบบแพลตฟอร์ม (Platform Admin) ได้ถูกต้องจริงหรือไม่
2. ทดสอบการเข้าสู่ระบบและตรวจสอบสิทธิ์ให้มั่นใจว่าเมื่อล็อกอินสำเร็จแล้ว ระบบจะนำทางผู้ใช้ไปยังเส้นทางหลัก `/platform` ได้อย่างราบรื่น
3. บันทึกและ Commit/Push การอัปเดต Middleware และการแยก Login ในรอบล่าสุด

### 💡 ทำไมต้องทำขั้นตอนนี้ (Rationale):
* **ความมั่นคงปลอดภัย (Security Isolation):** ป้องกันไม่ให้แอดมินของร้านค้าทั่วไป (Shop Owner/Staff) หลุดเข้ามาเข้าถึงหน้าระบบควบคุมหลักที่ดูแลร้านค้าทั้งหมด และยืนยันว่าผู้ใช้ระดับ Platform เท่านั้นที่เข้าถึงหน้านี้ได้
* **เพื่อความถูกต้องของข้อมูล (Routing Integrity):** เพื่อตรวจสอบให้แน่ใจว่า Middleware ที่จัดทำขึ้นมาเพื่อสกัดกั้นโดเมน `control` ไม่ให้ไปทับซ้อนกับระบบ Tenant Slug ทำงานได้อย่างไร้ข้อผิดพลาด ก่อนที่เราจะขยายระบบการกำหนดเส้นทาง (Routing) ในขั้นถัดไป

---

## 📌 ขั้นตอนที่ 2: ปรับปรุงระบบ Subdomain Routing ให้แข็งแกร่ง (Hardening Hostname-Based Routing)

### สิ่งที่จะทำ:
1. ปรับแต่งโครงสร้าง Dynamic Tenant Resolution ใน `apps/booking-consumer` และ `apps/booking-admin` ให้ดึงค่า Shop Slug และกำหนดตัวตนร้านค้าโดยอ้างอิงจาก Hostname (เช่น `[shop-slug].craftbikelab.com`) 100%
2. ปรับลดการพึ่งพาตัวแปรสภาพแวดล้อมเฉพาะเจาะจงแบบ Manual (`NEXT_PUBLIC_SHOP_ID`) ให้ทำหน้าที่เป็นเพียงตัวแปร Fallback สำรองสำหรับสภาพแวดล้อมสำหรับการพัฒนาในเครื่อง (Local Dev Environment) เท่านั้น
3. เขียนฟังก์ชัน Middleware/Utility ที่สกัดชื่อโดเมน/ซับโดเมนได้อย่างปลอดภัยในทุกกรณีการเชื่อมต่อ (รวมถึงการใช้งานแบบ Localhost ด้วย)

### 💡 ทำไมต้องทำขั้นตอนนี้ (Rationale):
* **การขยายตัวของระบบ (Scalability):** หากระบบยังผูกติดกับไฟล์ Env หรือการตั้งค่า Manual ของระบบทีละร้าน การขยายฐานลูกค้า SaaS ไปมากกว่านี้จะทำได้ยากและล่าช้า เพราะจำเป็นต้องสร้างตัวแปรหรือแก้โค้ดทุกครั้งที่มีร้านใหม่
* **ความเป็น Multi-tenant แท้จริง (True Multi-tenancy):** เพื่อให้ระบบสามารถจำแนกตัวตนร้านค้าและดึงการตั้งค่าเฉพาะของร้าน (เวลาทำการ วันหยุด บริการ) มานำเสนอให้แก่ลูกค้าได้อย่างถูกต้องแม่นยำ เพียงแค่อ่านค่าจากชื่อ URL ที่ลูกค้าเรียกเข้าใช้งาน

---

## 📌 ขั้นตอนที่ 3: ระบบการลงทะเบียนร้านค้าใหม่แบบขั้นตอนเดียว (One-Click Tenant Onboarding)

### สิ่งที่จะทำ:
1. พัฒนาระบบ Onboarding ภายในแผงควบคุม Platform Admin หรือสร้างหน้าเฉพาะเพื่อให้ผู้ดูแลระบบสามารถสร้างร้านค้าใหม่ได้จากหน้าเว็บโดยตรง
2. เขียน Store Procedure / Database Function ใน Supabase เพื่อให้การสร้างร้านค้าทำงานเป็นธุรกรรมเดียว (Single Transaction):
   * เพิ่มแถวข้อมูลร้านค้าในตาราง `shops`
   * สร้างสิทธิ์และเชื่อมโยงบัญชีเจ้าของร้านแรกในตาราง `shop_users`
   * จัดเตรียมค่าตั้งต้นของเวลาทำการ (Working Hours) และเวลาหยุดมาตรฐาน
   * ติดตั้งรายการบริการเริ่มต้น (Default Service Items) เพื่อลดภาระการตั้งค่าแรกเข้าของร้านค้า
3. ออกระบบทดสอบและตรวจสอบ DNS/Domain Mapping ของร้านใหม่แบบอัตโนมัติ

### 💡 ทำไมต้องทำขั้นตอนนี้ (Rationale):
* **ลดข้อผิดพลาดและความซับซ้อน (Operation Efficiency):** ปัจจุบันการเพิ่มร้านใหม่ต้องรันสคริปต์สควลหรือใช้ CLI ในการเพิ่มค่า ซึ่งเสี่ยงต่อการสะกดผิดหรือจัดเตรียมสิทธิ์ผิดพลาด การทำ UI/API สำหรับ Onboarding จะเปลี่ยนให้งานนี้ไร้ความเสี่ยงและทำเสร็จได้ในคลิกเดียว
* **ยกระดับประสบการณ์ผู้ใช้งาน (Self-Service & CX):** เป็นการปูทางให้เกิดระบบลงทะเบียนสมัครใช้งานร้านค้าแบบอัตโนมัติในอนาคต (เมื่อเชื่อมระบบชำระเงินเรียบร้อย) ช่วยให้แพลตฟอร์มดำเนินงานได้ด้วยตนเองโดยไม่ต้องอาศัยนักพัฒนาเข้าไปทำข้อมูลหลังบ้านให้

---

## 📌 ขั้นตอนที่ 4: การรวบรวม ตรวจสอบความเข้ากันได้ และ Verification (Build & Smoke Testing)

### สิ่งที่จะทำ:
1. การตรวจสอบและรันการ Build ของ Next.js ทั้ง 2 แอปพลิเคชัน (`apps/booking-consumer` และ `apps/booking-admin`) บนระบบ Local เสมือนจริง เพื่อดักจับ Type Error หรือโค้ดที่ไม่สมบูรณ์ก่อน Deploy
2. เขียนคู่มือการบำรุงรักษาและระบายปัญหา (Maintenance & Troubleshooting Guide) สำหรับกรณีที่เกิดปัญหาด้าน Domain Sync ระหว่างเครื่องของผู้ใช้
3. อัปเดตข้อมูลความรู้ทั้งหมดกลับลงสู่ `05-Agent-Memory` หรือสร้างบันทึกแบบ `_v2` ในส่วนที่เกี่ยวข้อง

### 💡 ทำไมต้องทำขั้นตอนนี้ (Rationale):
* **ความเสถียรของโปรดักชัน (Zero Downtime):** ป้องกันไม่ให้การพัฒนาส่งผลกระทบต่อร้านค้าจริงที่กำลังรันอยู่ (เช่นร้าน KMO RackBarCustom) โดยการทดสอบ Build และตรวจสอบ Type Safety ให้หมดจดก่อนอัปโหลดขึ้น Vercel
* **การประสานงานที่ไร้รอยต่อ (Handoff Continuity):** บันทึกการตัดสินใจการทำโค้ดและขั้นตอนการแก้ไขลงใน Vault อย่างถูกต้อง เพื่อให้ผู้ดูแลระบบ (มนุษย์) หรือ AI ตัวถัดไปที่ได้รับไม้ต่อ สามารถเข้าใจบริบทและทำงานต่อได้โดยไม่ต้องเสียเวลาวิเคราะห์ประวัติใหม่ทั้งหมด
