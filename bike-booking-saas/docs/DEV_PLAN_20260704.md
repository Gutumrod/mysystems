## ภาพรวมที่เจอ

**จุดแข็ง:**

- Trigger กันจองชนฝั่ง DB ออกแบบดี (advisory lock + ตรวจ capacity รายชั่วโมง + daily ข้ามวันหยุด)
- RLS เกือบครบทุกตาราง, SECURITY DEFINER ทุกตัวตั้ง `search_path` แล้ว
- Service role key ไม่รั่วฝั่ง client (ใช้ที่เดียวคือ `/api/signup` ฝั่ง server)
- โค้ดโดยรวมสะอาด ไม่มี dependency ฟุ่มเฟือย

**จุดวิกฤต:** มีช่องโหว่ account takeover 1 จุด (เฟส 0.1) และกับดักหลายจุดที่ต้องเคลียร์ก่อนขายจริง

## เฟส 2 — ~~Telegram Notification~~ → ตัดออกจากแผน (ตัดสินใจ 2026-07-04)

**เหตุผล:** กลุ่มเป้าหมาย (เจ้าของร้านมอเตอร์ไซค์ไทย) ใช้ **LINE** เป็นช่องทางหลัก ไม่ใช่ Telegram — ยืนยันจากโค้ดระบบเองด้วย (ฟอร์มลูกค้าและข้อมูลร้านมีช่อง LINE ID เป็นช่องทางติดต่อหลักทุกจุด ไม่มี Telegram ปรากฏใน UI ที่ไหนเลย) ต่อให้แก้ security ของ Telegram ครบ (webhook auth, RLS, per-shop chat_id) เจ้าของร้านก็ไม่น่าจะเปิดดูอยู่ดีเพราะไม่ใช่แพลตฟอร์มที่เขาใช้จริง — ไม่คุ้มกับต้นทุนแก้ที่มีอยู่จริง (ดูปัญหาเดิมด้านล่าง)

**สถานะไฟล์:** `supabase/config.toml`, `supabase/functions/telegram-notifier/`, `20260521000000_telegram_notifications.sql` — **เก็บไว้เฉยๆ ไม่ลบ ไม่แตะ ไม่ commit** (เผื่อใช้อ้างอิงโครงสร้าง outbox pattern ตอนทำเวอร์ชัน LINE ทีหลัง)

**ปัญหาเดิมที่เคยพบ (ยังจริงอยู่ ถ้าจะกลับมาทำ Telegram หรือย้ายไป LINE ต้องแก้เหมือนเดิม):**
- webhook ไม่มี auth เลย (`verify_jwt = false` + ไม่มี shared-secret) — ใครรู้ URL ก็ยิง replay ได้
- `notification_settings` ไม่มี RLS
- chat/channel id เดียวทั้งระบบ ไม่ per-shop — ขัด multi-tenant ถ้ามีร้านที่ 2
- ไม่มี sweeper กวาด event ค้าง `pending`, ไม่มี retention policy ของ payload ที่เก็บ PII ลูกค้าเต็มๆ

**ถ้าจะทำ notification จริงในอนาคต:** ทำเป็น LINE Notify / LINE Messaging API แทน ใช้โครง outbox pattern เดิมเป็นฐานได้ (แก้ endpoint + auth ปัญหาเดิมทั้งหมดข้างบนเหมือนกัน ไม่ว่าจะเป็น LINE หรือ Telegram)

ก่อนเริ่ม: เช็คกับ live ว่า migration ตัวนี้ apply ไปแล้วหรือยัง — ห้ามเดาจากไฟล์ local
